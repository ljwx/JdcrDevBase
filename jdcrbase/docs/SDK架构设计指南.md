# SDK 架构设计指南

这份文档用于设计和评审常规 SDK，尤其适合 Android / Kotlin SDK，也适用于网络、存储、音视频、设备能力等功能模块。

SDK 架构的目标不是类多、分层多或设计模式多，而是：

```text
对调用方：契约稳定、容易接入、出错后知道怎么办
对维护者：主流程清楚、资源归属明确、常见改动影响范围可控
对宿主 App：依赖克制、行为可预测、兼容性风险低
```

一句话判断：

```text
好的 SDK 架构 = 稳定的公开契约 + 清楚的内部所有权 + 可控的演进成本 + 较低的接入成本
```

---

## 1. SDK 与普通 App 功能的区别

App 内部代码可以随业务一起修改，SDK 发布后却运行在别人的进程、线程、依赖图和生命周期中。设计 SDK 时，要额外考虑：

- 调用方不会和 SDK 同时升级，旧 API 需要长期可用。
- 宿主 App 的线程、权限、前后台状态和资源占用不受 SDK 控制。
- SDK 的依赖可能与宿主的依赖版本冲突。
- SDK 出现问题时，维护者通常只能依赖日志、错误码和有限的现场信息。
- 一个“内部重构”也可能造成源码、二进制或行为不兼容。
- SDK 的默认行为会被大量调用方复制，错误设计发布后修正成本很高。

因此，SDK 首先是一份需要长期维护的公开契约，其次才是一组内部实现。

## 2. 推荐的设计顺序

不要先画包结构，也不要先创建接口。按下面顺序推进更稳妥。

### 第一步：定义用户和核心场景

先回答：

```text
谁在调用这个 SDK？
调用方最常见的 3 个场景是什么？
调用方最需要控制什么？
哪些细节应该由 SDK 自动处理？
哪些场景当前明确不处理？
```

“非目标”必须写出来。没有边界，设计会不断为低概率场景增加状态、接口和降级分支。

### 第二步：列出外部约束

```text
最低系统版本：
Kotlin / Java 调用要求：
线程要求：
权限要求：
进程和前后台限制：
性能和内存预算：
允许引入的依赖：
隐私和安全要求：
兼容的旧版本：
```

### 第三步：先写公开契约

先用调用方视角写出最短示例，再设计内部类。

```kotlin
val client = ExampleSdk.create(config)
val result = client.execute(request)
client.close()
```

从示例反推：创建、执行、取消、停止、释放、重试和错误报告分别应该是什么语义。

### 第四步：画主流程、失败流程和生命周期

至少画三条线：

```text
主流程：调用 -> 校验 -> 获取资源 -> 执行 -> 返回结果 -> 清理
失败流：在哪一步失败 -> 谁补充上下文 -> 谁转换公开错误 -> 谁清理
生命周期：创建 -> 可用 -> 工作中 -> 停止 -> 释放
```

### 第五步：确定所有权

明确谁拥有状态、资源、任务、队列和错误转换。所有权不清，后面加多少类都不会清楚。

### 第六步：识别真实变化点

列出未来一年最可能发生的 3～5 个改动，用它们验证边界，而不是猜测所有可能性。

### 第七步：先完成一条纵向主流程

先让一个真实场景从公开 API 走到平台实现并完成清理，再根据实际复杂度提取类和接口。

### 第八步：用测试和真实修改持续重构

架构通常是迭代出来的。第一版需要方向正确，不需要提前猜中所有未来。

## 3. 公开 API 是 SDK 最重要的设计

公开 API 需要明确的不只是参数和返回值，还包括时间、线程、生命周期和失败语义。

### 3.1 每个操作都要回答的问题

```text
什么时候算调用成功？
返回时工作已经完成，还是只提交了任务？
是否允许并发调用？
重复调用是幂等、报错还是创建新任务？
如何取消？取消后何时真正释放资源？
回调在哪个线程执行？
调用方回调阻塞或抛异常会怎样？
对象释放后还能否再次使用？
```

例如，`start()` 可以表示“请求已接受”，也可以表示“底层资源已经准备完成”。两种都能实现，但必须选定一种，并通过命名、返回值、状态或注释表达清楚。

### 3.2 API 保持小而完整

优先提供完成核心任务所需的最小接口。不要把每个内部开关都公开成配置；公开选项一旦发布，就会成为长期兼容负担。

一个配置是否值得公开，可以问：

- 调用方是否真的需要决定它？
- 不公开时，SDK 能否给出稳定合理的默认值？
- 它是否会因底层实现替换而失去意义？
- 发布后是否愿意长期维护它的行为？

### 3.3 同时考虑 Kotlin 和 Java

Android SDK 如果需要服务 Java 调用方，要检查：

- 默认参数是否需要工厂、Builder 或 `@JvmOverloads`。
- `suspend`、`Flow`、函数类型是否需要回调式适配层。
- 空安全在 Java 侧是否清晰。
- `object`、扩展函数、密封类型和默认接口方法的 Java 体验是否可接受。
- 异常和取消是否能被两种语言一致处理。

不要为了 Java 兼容破坏 Kotlin 主 API；可以用薄适配层提供两套自然的调用方式。

## 4. 兼容性不是只有“能编译”

SDK 兼容性至少有五个层面：

| 类型 | 含义 | 常见风险 |
| --- | --- | --- |
| 源码兼容 | 调用方重新编译仍能通过 | 改名、参数变化、重载歧义 |
| 二进制兼容 | 调用方不重新编译也能运行 | 删除方法、修改签名、改变父类 |
| 行为兼容 | 同样调用仍得到可接受的行为 | 默认值、线程、异常、时序改变 |
| 数据兼容 | 已保存的数据仍能读取 | 序列化字段、缓存格式变化 |
| 协议兼容 | 与服务端或设备仍能通信 | 字段、版本、握手和降级变化 |

发布 API 后遵循以下策略：

- 优先新增能力，不直接修改已有语义。
- 废弃旧 API 时，给出替代 API 和迁移说明，并保留合理周期。
- 不把第三方库类型直接暴露在公开 API 中，否则第三方升级会变成 SDK 破坏性变更。
- 默认值也属于行为契约，修改前必须评估影响。
- 为公开 API 建立自动化签名检查，避免无意中的二进制变化。

## 5. 内部结构：按稳定边界分，不按名词数量分

一个常见但不强制的结构是：

```text
Public API / Facade
        |
Use case / Session / Coordinator
        |
Domain policy and model
        |
Platform or third-party adapter
```

| 层次 | 主要职责 |
| --- | --- |
| Public API / Facade | 对外契约、参数入口、公开状态、生命周期命令 |
| Coordinator | 编排一次业务流程，决定步骤、取消、重试和清理顺序 |
| Policy / Model | 与平台无关的规则、状态转换、数据模型 |
| Adapter | 隔离 Android、网络、数据库、编解码器等具体实现 |

这不是要求每层都建包、接口和实现。小功能可以把 Coordinator 和 Policy 放在同一个类或文件中；只有边界能降低复杂度时才拆开。

### 包结构建议

优先按功能聚合，再区分公开与内部，而不是为每种技术名词创建一个包。

```text
com.example.sdk
├── ExampleSdk.kt                 主要公开入口
├── config/                       稳定的公开配置
├── model/                        稳定的公开模型
├── exception/                    稳定的公开错误
├── featureA/
│   ├── FeatureAClient.kt         功能公开入口
│   └── internal/                 编排和平台实现
└── internal/                     SDK 共享但不公开的实现
```

目录应该帮助定位代码，而不是展示“架构很完整”。只有一两个文件时，不必单独建包。

## 6. 职责分离的实际判断标准

单一职责不是“一个动作一个类”，而是“一个对象只有一个主要变化原因，并完整拥有它负责的规则”。

### 值得建立独立边界的情况

- 它拥有独立资源和完整生命周期。
- 已经存在两个真实实现，而不是猜测以后可能有。
- 它隔离了平台或第三方库细节。
- 它包含一组必须共同维护的不变量。
- 它是高概率的独立变化点。
- 独立测试能显著降低验证成本。

### 通常不值得拆类的情况

- 只有一个调用者，只做参数转发。
- 没有自己的状态、资源或策略。
- 接口和实现永远一对一，且没有真实替换需求。
- 拆开后主流程需要频繁跨文件阅读。
- 类名只是某个动作，没有形成稳定概念。

可以做“删除测试”：删除某一层后，如果代码更短、更容易理解，同时没有丢失约束、隔离或可测试性，这一层大概率不需要存在。

## 7. 所有权比类数量更重要

| 关注点 | 必须回答的问题 | 推荐默认值 |
| --- | --- | --- |
| 公开状态 | 谁能修改？ | 一个门面或会话对象统一写入 |
| 底层资源 | 谁创建、谁最终释放？ | 创建者负责最终释放 |
| 协程 / 线程 | 谁创建、谁取消、谁等待结束？ | 与业务对象生命周期一致 |
| 队列 | 谁关闭，关闭后生产者如何退出？ | 一个明确所有者 |
| 重试 | SDK 自动重试还是调用方决定？ | 只自动重试明确安全且幂等的操作 |
| 错误转换 | 谁把底层错误变成公开错误？ | 最接近公开边界且掌握业务语义的层 |

状态、资源和任务如果分别由多个对象维护，即使每个类都很小，整体仍然会很难理解。

## 8. 生命周期与状态设计

只建模调用方能观察到、能据此做决策的状态，不要把每个内部步骤都公开。

常见的长任务状态：

```text
Idle -> Starting -> Running -> Stopping -> Stopped
                    |                    |
                    +------ Failed <----+

任意可用状态 -> Released
```

逐个确认：

- 哪个事件触发状态转换？
- 转换前后底层资源分别是什么状态？
- 最终状态在资源清理前还是清理后发布？
- 同一个命令重复调用如何处理？
- `release` 与正在运行的任务竞争时，谁决定最终状态？
- 失败后对象可以重用，还是必须重新创建？

### 回调只是里程碑，不表示函数结束

```kotlin
suspend fun run(onStarted: (Info) -> Unit)
```

```kotlin
session.run(::onSessionStarted)
```

等价于：

```kotlin
session.run { info ->
    onSessionStarted(info)
}
```

`onStarted(info)` 只报告某个里程碑。调用后，`run` 仍然可以继续执行整个长任务：

```text
run 开始
  -> 初始化资源
  -> onStarted(info)
  -> 持续工作
  -> 停止或失败
  -> finally 清理资源
run 返回或抛出异常
```

所以 `run(...)` 后面的代码表示“整个任务结束后做什么”，不是“启动回调后立刻做什么”。这种时序必须通过命名、注释或状态契约表达清楚。

## 9. 并发设计先写规则，再选工具

不要从 `Mutex`、`AtomicBoolean`、`Channel` 或线程池开始设计。先写规则：

```text
公开方法是否线程安全？
同一对象最多允许几个并发任务？
取消是立即返回，还是等待清理完成？
回调在哪个线程执行？
队列满时等待、丢弃、覆盖还是失败？
慢调用方能否阻塞 SDK 核心线程？
SDK 自己创建作用域，还是使用调用方作用域？
```

再为每条规则选择最小机制。

推荐原则：

- 不使用无法管理生命周期的全局任务。
- SDK 创建的线程、作用域和队列必须有关闭路径。
- 不用多个原子变量、状态流和 Job 重复表达同一个事实，除非各自职责明确。
- 不在持锁期间执行调用方代码、IO 或可能阻塞的操作。
- 取消与业务失败要能区分；取消时仍要完成必要的资源清理。
- 回调和监听器必须有移除机制，避免宿主对象泄漏。

## 10. 配置与扩展点

### 配置设计

- 配置对象优先不可变，创建后行为可预测。
- 能在构造时发现的开发者错误，用 `require` 尽早校验。
- 全局配置和单次请求参数分开，避免修改全局配置影响运行中的任务。
- 默认值选择最通用、最稳定的行为，而不是实验性最强的行为。
- 配置之间存在组合约束时，在一个位置统一校验。

### 扩展点设计

不要因为“以后可能替换”就为所有类建立接口。扩展点适合放在：

- 已经有多个真实实现的位置。
- 业务明确允许调用方注入策略的位置。
- 平台或第三方实现需要隔离的位置。
- 测试确实需要替换，且替换能验证重要契约的位置。

扩展接口一旦公开，就要承担兼容责任。内部扩展点可以先保持 `internal`，等需求稳定后再公开。

## 11. 异常与结果模型

异常分类应该帮助调用方决定下一步，而不是复述底层类名。

```text
参数或配置错误：调用方式有误，需要修改代码
前置条件不满足：缺权限、未初始化或对象已释放
暂时不可用：资源忙、网络不可用，可稍后重试
任务失败：本次任务结束，可按业务决定是否重启
协议或数据错误：输入或对端不符合契约
内部错误：SDK 未预期的问题，需要日志和版本信息定位
```

推荐原则：

- 开发阶段可立即发现的静态配置错误，可以使用 `require`。
- 权限、设备能力、网络、资源竞争和生命周期等运行时问题，如果调用方能够恢复，应返回稳定结果或公开异常，不要随意用 `check` 产生 `IllegalStateException`。
- 不直接暴露第三方异常作为公开契约；保留原始异常为 `cause`，同时转换为稳定的 SDK 语义。
- 不为每条错误信息创建异常子类，只区分调用方处理方式确实不同的类别。
- 清理阶段的错误不能覆盖真正导致任务失败的原始错误，可以作为 suppressed cause 或诊断信息保留。

## 12. 依赖与宿主兼容

SDK 的依赖也是公开成本。

- 默认使用 `implementation` 隐藏内部依赖，只有公开签名必须暴露时才使用 `api`。
- 避免在公开 API 中出现第三方类型。
- 控制依赖数量、体积、初始化耗时和传递依赖。
- 评估常见依赖与宿主不同版本共存时的风险。
- 不在未明确授权时修改全局单例、系统代理、默认线程策略或进程级配置。
- Android SDK 要验证最低系统版本、R8/ProGuard、资源命名冲突和 Manifest 合并结果。
- 必要的 consumer rules 由 SDK 提供，不把内部混淆细节转嫁给调用方。
- 自动初始化必须轻量、可预测；重任务应延迟到真正使用时。

## 13. 日志、诊断与隐私

日志的目标是让维护者还原流程，而不是打印每一行执行轨迹。

一条有效日志通常包含：

```text
阶段 + 结果 + 必要上下文 + 可行动原因
```

推荐做法：

- 为一次请求或会话提供稳定标识，便于串联日志。
- 在开始、关键状态转换、降级、结束和异常处记录，避免循环中刷屏。
- 同一异常不要每层重复打印；在补充关键上下文、吞掉异常或到达任务边界时记录。
- 允许宿主接入自己的日志系统，并可关闭 SDK 日志。
- 不记录 token、密码、完整请求体、音频内容或其他敏感数据。
- 错误信息面向事实，不把推测写成确定原因。

## 14. 性能与资源预算

先定义可接受预算，再优化：

```text
初始化耗时：
单次调用延迟：
常驻内存：
临时内存峰值：
线程数量：
队列上限：
网络和磁盘开销：
```

重点防止无上限增长：无限队列、无限重试、未关闭线程、永久缓存和未移除监听器。性能策略本身也是行为契约，例如背压时等待、丢弃还是失败，必须明确。

## 15. 用变化场景验证架构

不要只看类图是否整齐。列出真实改动，逐个走查需要修改哪些文件、状态和测试。

| 变化场景 | 理想影响范围 |
| --- | --- |
| 更换 HTTP、数据库或平台实现 | 对应 adapter 和组装位置 |
| 新增一种输出或处理策略 | 新实现和组装位置 |
| 修改重试、背压或取消规则 | Coordinator / policy |
| 修改公开状态或重复调用语义 | Facade 和契约测试 |
| 新增 Java 调用方式 | 公开适配层，不侵入核心实现 |
| 调整日志实现 | 日志适配器，不修改业务流程 |
| 升级第三方库 | 内部 adapter，不影响公开模型 |

如果一个常见改动必须同时修改所有层，边界可能切错；如果每个改动都要新增接口和类，抽象可能过度。

## 16. 测试策略

优先验证公开契约，而不是私有类的摆放方式。

### 必要测试层次

- 纯规则单元测试：状态转换、参数校验、重试和数据转换。
- 生命周期测试：启动、取消、停止、释放以及重复调用。
- 失败路径测试：每个资源获取点和外部调用点失败时都能正确清理。
- 并发测试：关键竞争条件、回调重入、慢消费者和取消。
- Adapter 集成测试：平台 API、网络、数据库或编解码真实行为。
- 公开契约测试：Kotlin 和 Java 的典型接入方式。
- 发布检查：公开 API 签名、R8/ProGuard、最低系统版本和示例工程。

测试应该允许内部重构。只要公开行为、状态和资源结果不变，私有类合并或移动不应导致大量测试失败。

---

## 17. 常见过度设计信号

- 一个简单主流程要跨很多包才能读完。
- 大量类只有一个方法，并且只转发参数。
- 每个实现都有一对一接口，却没有真实替换需求。
- 多个对象维护相似的状态和停止标记。
- 为假设中的未来需求暴露大量配置。
- 使用设计模式的理由只是“架构应该这样”。
- 新增一个小功能必须同时修改许多无关层。
- 测试主要验证 mock 调用次数，而不是业务契约。

复杂度没有消失，只是在类、调用层级和状态同步之间转移。每增加一层，都要能说出它具体隐藏了什么复杂度。

---

## 18. 架构评审快速清单

```text
[ ] 新调用方能否通过一个最短示例完成核心任务？
[ ] 公开 API 的成功、失败、取消、停止和释放语义是否明确？
[ ] Kotlin 和 Java 调用体验是否符合目标用户？
[ ] 源码、二进制、行为、数据和协议兼容性是否评估？
[ ] 每个资源、任务、队列和状态是否有唯一明确的所有者？
[ ] 主流程能否在 10～15 分钟内读懂？
[ ] 是否只为真实变化建立边界？
[ ] 是否有只转发参数、没有规则的多余层？
[ ] 运行时可恢复问题是否使用了稳定错误，而不是随意崩溃？
[ ] 依赖是否克制，第三方类型是否泄漏到公开 API？
[ ] 所有线程、协程、监听器和资源是否有关闭路径？
[ ] 日志能否还原关键流程，同时避免重复和敏感信息？
[ ] 测试是否覆盖公开契约、失败路径和清理结果？
[ ] 常见修改能否局部完成？
```
